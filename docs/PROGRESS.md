- Not automated: truly parallel PATCH/lock races, the client delete-vs-write race, and a concurrent double stock commit (all need two committed connections; the row locks, advisory locks and version checks are exercised sequentially).

- A stock upload can be undone only from its result dialog; there is no list of past uploads.

- D-61 left open: type-to-confirm, "Today", sticky menu-plan columns, sidebar compaction.
- Small duplications kept on purpose: `needAdmin` guards per service, header-alias maps in `src/lib/import/{items,recipes}.ts`.
- Add-recipe B1: a restore (backup) does not carry revisions and leaves existing ones alone until B4; revisions are archived only when something starts a new one, so a card edited in place for a long time has one revision (press Start new revision before a change worth keeping); "Replaced by" on an archived revision is who started the next one; deleting a sub-recipe that an archived parent still uses is not blocked; the 8 Stock class gaps below still apply.
- Add-recipe A1/A2: the Stock class and the 6-row default are not columns of the Excel layout (an upload leaves the stored class alone); Export card reads the saved card, so an edit typed a second before the click can be missing from the file; the `card` export parameter is ignored by every export kind except `recipes-data`; the recipe list counts only rows with a code; an upload that turns a Menu card into a Sub-Recipe clears the class; an older backup restores cards with the class not set.
- Behaviour to remember: the recipe list is ordered by code (legacy used array order); ingredients missing from a restored backup are **kept** (history cascades otherwise), only cards are soft-deleted.
